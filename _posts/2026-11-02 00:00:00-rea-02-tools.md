# 工具面：172 个契约，先做能力协商

一个 MCP 工具对模型的价值，和它占的上下文成反比。

每个工具都要广播名字、描述、输入 schema、输出 schema；模型每轮都要带着这些 token 做选择。工具少的时候这不是问题，工具到几百个的时候，"把目录全发出去"本身就是一种设计失败。REA 的源码里有 172 个工具契约名，它没有把这个问题留给客户端。

## 先分族，再决定发不发

`src/contracts/toolFamilyIds.ts` 定义了 18 个工具族：

```text
direct, enhanced, native, artifact, managed, firmware, android,
pcap, flutter, frida, apktool, jeb, adb, browser, electron,
javascript-runtime, application, session
```

启动时可以用 `REA_MCP_TOOL_FAMILIES` 只声明这次会话需要的族。`src/config/mcpToolFamilies.ts` 的注释把动机写得很直白：

```ts
// Agents pay context for every advertised tool schema. Scoping a registration
// to the families a workflow needs keeps the unneeded schemas out of the
// session entirely; out-of-scope tools stay registered but disabled.
```

注意后半句：不是不注册，而是注册但禁用。这样目录身份仍然稳定，调用一个未启用的工具会得到明确的拒绝，而不是"这个工具不存在"的幻觉。默认输入 schema 也是紧凑版；需要完整字段说明时，用 `REA_MCP_INPUT_SCHEMA_PROFILE=full` 显式打开。

## 六种工具形状

`docs/tool-design.md` 把工具按"分析任务"分成六类，而不是按前缀：

| 形状 | 回答的问题 | 例子 |
|:--|:--|:--|
| `inspect` | 这个对象是什么 | `inspect_go_binary`、`inspect_pe_imports` |
| `search` / `list` | 有哪些候选 | `list_procedures`、`search_strings` |
| `trace` | 它们怎么连起来 | `trace_application_feature`、`build_call_path` |
| `compare` | 两边差在哪 | `compare_functions`、`compare_artifacts` |
| `workflow` | 一个反复出现的组合问题 | `verify_reconstruction` |
| `observe` / `capture` | 运行时到底做了什么 | `capture_process_scenario`、`capture_browser_scenario` |

这个分类的意义在于：新增工具时先问"它改变的是哪一种结论"，而不是"上游引擎还有哪个 API 没包"。文档里还有一条硬规矩：不要在一个工具里塞进无关的发现、执行和修改模式。

## 副作用是契约的一部分

REA 给每个公开工具维护一份 `ToolEffects`，十个布尔值：

```ts
mutatesTarget, mutatesSession, writesFilesystem, launchesProcess,
accessesNetwork, changesUiState, mayDiscardData,
executesForeignCode, mutatesDevice, idempotent
```

它们再被映射成 MCP 的四个 annotation：`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`。比如 `cutter_command` 同时打开 `mutatesTarget`、`executesForeignCode`、`writesFilesystem`、`launchesProcess`、`accessesNetwork`、`changesUiState`，而 `inspect_go_binary` 只有 `mutatesSession`。

这比在描述里写"这个工具会修改目标"可靠得多。客户端可以在调用前做审批，模型也可以根据 `destructive` 决定要不要先问用户。副作用不是文档，是 schema。

## 不可用也要说清楚

很多工具在特定宿主上根本跑不了：Linux 没有 `prlimit` 就不能跑 TShark，Windows 没有 Job Object 就不能做某些进程隔离，没装 Ghidra 就没有深分析。REA 的选择不是把工具藏起来，而是让 `binary_session` 返回一份可用性清单：

- `name`、`surface`、`default_mode_available`、`modes`
- `effects`、`annotations`
- `client_requirements`（required / optional / missing）
- `available`、`reason`、`remediation`

不可用原因被收敛成六种：`client_capability_missing`、`target_required`、`provider_missing`、`provider_unavailable`、`target_unsupported`、`unsupported_host`。每种对应不同的修复动作——装引擎、换宿主、先开目标，或者换客户端能力。把"没装"和"权限被拒"都叫"不可用"，模型就只能瞎试。

## 提示词也是目录的一部分

除了工具，REA 还暴露 6 个 MCP prompt：`investigate_feature`、`compare_application_versions`、`verify_reconstruction`、`trace_crash`、`audit_residual_unknowns`、`prepare_bounded_process_capture`。它们不调用工具，只渲染调查步骤；不支持 prompt 的客户端可以用 `guided_workflows` 工具拿到同样的文本。

技能包本身也能被检索：`search_guidance` 在安装好的技能文件里按问题找章节，`read_guidance_section` 按 locator 读回原文。这样模型不需要一次把 2,480 行技能全塞进上下文。

## 这一层的设计原则

一句话：**目录要完整，暴露要协商，副作用要声明，不可用要解释。**

工具数量本身不是问题，问题是把选择成本转嫁给模型。REA 把选择成本拆成了四份：工具族决定"这次带哪些"，紧凑 schema 决定"每个带多少"，effects 决定"调用前要注意什么"，availability 决定"为什么不能用"。
