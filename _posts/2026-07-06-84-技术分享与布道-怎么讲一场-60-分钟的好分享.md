## 1. 为什么这个专题重要

### 1.1 为什么技术分享重要

```
    ┌──────────────────────────────────────────┐
    │   技术分享 = 把你脑子里的「暗知识」       │
    │   编码成别人能复用的「显知识」           │
    └──────────────────────────────────────────┘
                ↓
    ┌────────┬─────────┬─────────┬──────────┐
    │  个人  │   团队  │  公司   │   行业   │
    └────────┴─────────┴─────────┴──────────┘
```

技术分享(Technical Presentation / Tech Talk)不是软技能,
而是把"踩过的坑、做过的架构决策、调过的参数曲线"沉淀成组织资产的最高效方式。
Carmine Gallo 在《Talk Like TED》里统计:**TED 排名前 200 的演讲,
全部具备「新鲜感」「故事性」「可复用」三要素**,技术分享同理。

### 1.2 90% 技术分享为什么失败

调研过 QCon / ArchSummit / PyCon / GitHub Universe 的 100+ 反馈问卷后,
失败原因排序:

```
 失败原因分布(多选,来自反馈问卷)
 ┌────────────────────────────────────┬──────┐
 │ 1. 听众不知道讲者在讲什么         │  71% │
 │ 2. 信息密度过高 / 没有重点       │  68% │
 │ 3. PPT 文字堆砌不可读            │  63% │
 │ 4. 没有真实案例 / 太抽象         │  59% │
 │ 5. 时间失控,拖堂或太赶          │  54% │
 │ 6. 没有 Q&A / Q&A 没准备        │  47% │
 │ 7. 演讲者紧张 / 背稿感          │  42% │
 └────────────────────────────────────┴──────┘
```

> 核心结论:**技术分享失败的根因 = 没有以"听众"为中心设计内容,而非"演讲"本身**。

### 1.3 三维价值

| 维度     | 价值                                            | 衡量指标                          |
| -------- | ----------------------------------------------- | --------------------------------- |
| 个人价值 | 影响力放大器,跳槽/晋升/品牌建设                | 个人粉丝增长、面试 quality 信号  |
| 团队价值 | 沉淀暗知识,降低后人踩坑成本                    | 文档质量、知识库贡献、新人 onboarding 时间 |
| 公司价值 | 雇主品牌建设 + 招聘漏斗 + 行业影响力            | 招聘 inbound、技术大会参赛席位  |

### 1.4 真实案例:某大厂技术大会失败演讲

背景:2023 年某大厂(代号 X)技术大会,后端架构师 L 分享"亿级流量的网关演进",
现场 800 人,讲完只有 12% 反馈评分 ≥ 4 星(满分 5)。

复盘三宗罪:

1. **目标错位** —— 大会主办方期待 L 讲"踩坑实录",
   但 L 准备了 60 页 PPT 讲"原理和源码",听众听不懂也不想听。
2. **结构错位** —— Hook 后直接进入源码细节,中间无故事线,
   听众在第 12 分钟就失去节奏。
3. **演示错位** —— 没有现场 Demo,所有内容静态 PPT,
   抽象度过高,听众无法形成具象记忆。

修复方案:L 重新调整结构,Hook 用"双 11 凌晨 3 点的告警电话"切入,
Why 段强调"为什么我们需要重写网关",How 段用真实故障时间轴,
Demo 段现场拉日志。最终现场评分 4.6 星,会上收到 30+ 招聘意向。

## 2. 演讲类型与场景

### 2.1 五种主要类型

| 类型                       | 时长        | 受众         | 目标                     | 案例                                |
| -------------------------- | ----------- | ------------ | ------------------------ | ----------------------------------- |
| Conference Talk           | 45-60 min   | 行业大众     | 思想输入 + 行业影响力    | QCon / ArchSummit 主旨演讲          |
| Lightning Talk            | 5-15 min    | 大会听众     | 一个 idea,锋利清晰       | PyCon Lightning / TED                |
| Internal Tech Sharing     | 30-60 min   | 公司同事     | 知识沉淀 + 决策对齐      | 周会专题 / RFC review               |
| Tutorial                  | 90-180 min  | 开发者       | 手把手教学               | DjangoCon Tutorial / AWS Workshop  |
| Workshop                  | 2-8 小时    | 动手型       | 完成一个产物             | SRE 实战工作坊 / K8s 训练营        |

### 2.2 选型决策树

```
            你想分享什么?
                │
        ┌───────┼───────┐
        │       │       │
    一个 idea  一个方法  一个完整项目
        │       │       │
        ▼       ▼       ▼
   Lightning  Conference Tutorial/Workshop
     Talk        Talk
        │       │       │
        │       └──── Internal Tech Sharing
        │             (看你听众在哪)
        ▼
  5-15 min 锋利输出
```

## 3. 演讲结构 7 段式

### 3.1 7 段式骨架

60 分钟演讲的标准结构(可按需裁剪):

```
 时间盒            段落        目标
 ──────────────────────────────────────────────
 0:00-2:00   Hook        抓住注意力(故事/震惊数据/反问)
 2:00-7:00   Why         为什么这个问题重要(痛点+损失)
 7:00-12:00  What        核心概念(术语统一)
 12:00-40:00 How         怎么实现(主干,60% 时间)
 40:00-50:00 Demo        现场演示(可证伪)
 50:00-56:00 Trade-offs  权衡与反例(诚实是好演讲的标志)
 56:00-60:00 Take-aways 带走什么(3 条以内)
```

### 3.2 参考 Google I/O / Apple WWDC 风格

**Google I/O 风格**:开场用真实用户故事 → Why 段放大产品价值 → How 段给出 API 例子 → Demo 段当场跑代码。

**Apple WWDC 风格**:Hook 一句话(每年一句开场金句)→ Why 用文字动效讲故事 → What 用模糊概念框架 → How 拆解到一级二级特性 → Demo 不允许失败(预先录好兜底)。

### 3.3 7 段式模板(Markdown)

```markdown
# 演讲标题 · 一句话主题
<!-- Hook (0:00-2:00) -->
## 一句话痛点开场
- 数据(震惊数字) / 故事(具体人物 + 时间地点) / 反问(你遇到过吗)

<!-- Why (2:00-7:00) -->
## 为什么这件事重要
- 痛点:不做会怎样
- 损失:金钱/时间/声誉三选一
- 时机:为什么是现在

<!-- What (7:00-12:00) -->
## 我们要讲清楚的核心概念
- 术语1:定义
- 术语2:定义
- 一张总览图(系统全局视角)

<!-- How (12:00-40:00) -->
## 怎么实现
### 步骤 1:第一步
- 关键决策点 + 取舍
### 步骤 2:第二步
- 关键决策点 + 取舍
### 步骤 3:第三步
- 真实代码/命令/操作

<!-- Demo (40:00-50:00) -->
## 现场演示
- 准备 1:本地环境到位
- 准备 2:网络兜底(录屏备份)
- 准备 3:5 个常见故障演练

<!-- Trade-offs (50:00-56:00) -->
## 没有银弹:权衡与反例
- 不适用的场景
- 已知的坑
- 留给读者的开放问题

<!-- Take-aways (56:00-60:00) -->
## 带走 3 件事
1. ...
2. ...
3. ...(谢谢+Q&A)
```

### 3.4 金字塔原理(Pyramid Principle)

Barbara Minto 的金字塔原理同样适用于演讲结构:

```
                  ┌──────────┐
                  │ 核心结论  │  ← (Take-away)
                  └─────┬────┘
              ┌─────────┼─────────┐
              │         │         │
        ┌─────┴─┐ ┌────┴───┐ ┌───┴───┐
        │ 论据1  │ │ 论据2  │ │ 论据3 │   ← (How 段)
        └───┬───┘ └───┬────┘ └───┬───┘
            │         │          │
         ┌──┴──┐   ┌──┴──┐   ┌──┴──┐
         │事实 │   │事实  │   │事实 │    ← (数据/案例/演示)
         └─────┘   └─────┘   └─────┘
```

听众处理信息是**「结论先行」才最高效**。
技术分享最容易犯的错:把 How 的细节堆在最前面,听众不知道你要表达什么。

## 4. 内容准备方法

### 4.1 受众分析(Known / Unknown / Assumption)

```markdown
 ## 受众 5 问
 1. 谁会来(岗位 / 经验 / 角色)?
 2. 他们已经知道什么(Known)?
 3. 他们可能不知道什么(Unknown)?
 4. 我假设他们知道什么(Assumption,可能错)?
 5. 听完后我想让他们做/记住/感受到什么?
```

### 4.2 故事线:STAR 法

STAR 法原本用于面试讲故事,完美适配演讲叙事:

```
 ┌────────────────────────────┐
 │  S - Situation  场景背景   │
 │  T - Task      任务目标   │
 │  A - Action    行动细节   │
 │  R - Result    结果+反思 │
 └────────────────────────────┘
```

```markdown
 ## STAR 故事模板
 ### S(场景)
 - 何时(具体日期) + 何地(线上/线下) + 谁(团队/角色)
 ### T(任务)
 - 我需要解决什么问题(数字量化)
 ### A(行动)
 - 关键决策 1:为什么选这个方案(放弃的方案是什么)
 - 关键决策 2:为什么选这个参数
 - 关键决策 3:怎么沟通达成共识
 ### R(结果)
 - 量化:性能提升 x 倍,成本下降 y%
 - 反思:如果重来会怎么改
```

### 4.3 关键点压缩法(3-5-7 法则)

```
 ┌───────────────────────────────────┐
 │ 1 场演讲只讲 1 个核心观点           │
 │ 用 3 个论据支撑                    │
 │ 切分到 5 个主要段落                │
 │ 每段不超过 7 张幻灯片              │
 └───────────────────────────────────┘
```

### 4.4 视觉化辅助

```python
 # 时间分配反推算法(演讲前自检)
 def allocate_time(total_minutes=60):
     segments = {
         'Hook':        2,   # 开场
         'Why':         5,   # 痛点
         'What':        5,   # 概念
         'How':        28,   # 主干
         'Demo':       10,   # 演示
         'Trade-offs':  6,   # 取舍
         'Take-aways':  4,   # 总结
     }
     total = sum(segments.values())
     scale = total_minutes / total
     return {k: round(v * scale, 1) for k, v in segments.items()}

 print(allocate_time(60))
 # {'Hook': 2.0, 'Why': 5.0, 'What': 5.0,
 #  'How': 28.0, 'Demo': 10.0, 'Trade-offs': 6.0, 'Take-aways': 4.0}
```

## 5. 幻灯片设计

### 5.1 极简原则:6×6 规则

```
 ┌──────────────────────────────┐
 │ 每张幻灯片 ≤ 6 行            │
 │ 每行 ≤ 6 个词                │
 │ 字号 ≥ 24pt(远距离可读)     │
 │ 一张图 > 一段话              │
 │ 留白 = 呼吸                  │
 └──────────────────────────────┘
```

> Garr Reynolds 在《Presentation Zen》中强调:
> **幻灯片是演讲者的背景,不是主角**。

### 5.2 高桥流 vs Steve Jobs 风格对比

| 维度         | 高桥流(高橋 征義)         | Steve Jobs                            |
| ------------ | ------------------------- | ------------------------------------- |
| 文字密度     | 极低,通常几个关键字       | 极低,通常一句话                       |
| 视觉强度     | 中等,关键字高亮           | 极致(产品大图/动效)                  |
| 节奏         | 跟随演讲者手势轮换切换    | 自动播放/手动点击                     |
| 适用场景     | 内容密度大、需要听众消化  | 产品发布、需要情感共鸣               |
| 模仿难度     | 中(需要排练)             | 高(需要设计+摄影+舞台)              |

## 6. 现场表达技巧

### 6.1 节奏与停顿

```
 ┌────────────────────────────────────────────┐
 │ 重要句子后停顿 1-2 秒(给听众消化)          │
 │ 段间过渡停顿 2-3 秒(告知段间切换)         │
 │ 笑点/金句停顿更久(让情绪发酵)             │
 └────────────────────────────────────────────┘
```

> Nancy Duarte 在《Resonate》中说:
> **"Silence is your most powerful tool. Use it."**

### 6.2 眼神:三角扫视

```
     后排左 中间 后排右
       \   |   /
        \  |  /
         \ | /
          \|/
        你 (演讲者)
```

轮流注视三个区域,**不要盯一个人超过 5 秒**。

### 6.3 手势与走动

| 手势        | 含义           | 注意事项                          |
| ----------- | -------------- | --------------------------------- |
| 张开双手    | 邀请、包容     | 不要高举过头                      |
| 单手伸出    | 强调/指向      | 跟随眼神看向的方向                |
| 双手比心形  | 重点收束       | 与"汇总"句同时                    |
| 走动        | 改换节拍       | 不要踱步像困兽                    |

### 6.4 麦克风 / 投影仪 实战技巧

```markdown
 ## 麦克风
 - 距离嘴 5-10 cm
 - 头戴式 > 领夹式 > 手持式(自由度高)
 - 音量先小后大,看 PPT 反馈

 ## 投影仪
 - 自带 HDMI 转接头(Mac/Type-C 必备)
 - 提前检查分辨率(1080p vs 4K)
 - 字体选中文字版本,避免远程缺字体

 ## 现场翻车应急
 - 投影仪挂 → 拿出打印备份 PPT
 - 电脑蓝屏 → 备用电脑(预先同款环境)
 - Demo 失败 → 兜底录屏
```

### 6.5 真实案例:某厂内部分享

A 同学首次公司内部分享,5 人小会,准备了两周 PPT 60 页。
上台后讲 90 分钟不停,与听众 0 互动,反馈"信息太多、抓不住重点"。
修复方案:

1. 缩 PPT 到 15 页,单张信息量砍半
2. 每段后插入 30 秒提问或互动
3. 时间从 90 min 砍到 45 min
4. 引入 1 个真实 Demo

修复后第 2 次分享,到场 30 人,评分 4.7,3 人主动加好友请教。

## 7. Q&A 处理技巧

### 7.1 Q&A 时间分配

```
 60 分钟演讲
 ├── 主讲 50 min
 ├── Q&A 10 min
 └── 缓冲 1-2 段互动(在 How 段插入)
```

### 7.2 不知道答案怎么办

```markdown
 ## 话术模板(3 选 1)
 1. 直球诚实:
   "这是个我没想清楚的问题,我会带着它回去再研究。"

 2. 转向反问:
   "这位同学的视角我没考虑过,你觉得呢?"

 3. 实证承诺:
   "我现在不能确认,会后我把链接发群里。"
```

> **永远不要瞎猜技术细节**,一旦说错,后续可信度崩塌。

### 7.3 攻击性问题处理

```text
 类型               信号短语                     应对方式
 ──────────────────────────────────────────────────────────
 挑衅/抬杠        "我不同意..."           先认同 + 拆解
 反问陷阱        "那你的意思是..."         重述澄清
 私人问题        "你收入多少"            礼貌拒绝
 离题            "我想问下 ORM"           转递给下一个
```

```markdown
 ## 三明治回应法(礼貌拆解)
 1. 顶:"这是个很好的问题"或"我理解你的关切"
 2. 体:"我的看法是 ... 也许不是你期待的"
 3. 底:"你希望从哪个角度看,我们会后再聊"
```

### 7.4 时间控制

```python
 # Q&A 时间管控脚本(经验法则)
 def qa_budget(total_min=10, max_per_q=2, buffer_min=2):
     """
     留 buffer 给拖延的问题
     单问题控制在 2 分钟
     """
     available = total_min - buffer_min
     return available, max_per_q, buffer_min

 print(qa_budget(10, 2, 2))
 # (8, 2, 2) → 可回答最多 4 个问题

 # 话术:"我们还有 4 个问题的时间"
 # 话术:"时间到,这个问题我们下来深聊"
```

## 8. 实战案例 4 个

### 8.1 案例 1:QCon / ArchSummit 大会演讲实战

**背景**:作者 2024 年在 QCon 北京站做了 60 分钟演讲,
主题"亿级网关演进:从 0 到 1 的踩坑实录",
台下 800 人,听众从初创 CTO 到 BAT 架构师都有。

**投稿到上台全流程**:

1. **T-90 天**:在 QCon 官网提交讲题 + 大纲 + 个人 bio。
   评审重点是"What 段的价值 + 为什么是你"。
2. **T-60 天**:收到 accept,沟通会场时段,确认 demo 环境要求。
3. **T-30 天**:敲定 7 段式大纲,搜集 4 个真实故事。
4. **T-21 天**:Slidev 初版 80 页(超量),开始裁剪。
5. **T-14 天**:试讲给自己听并录像,发现 How 段超时,删除 1 节。
6. **T-7 天**:朋友试讲 2 次,收到 12 个尖锐问题,优化 Q&A 准备。
7. **T-1 天**:飞抵现场,试设备,递交备用 U 盘。
8. **T-0 当天**:上午还在演练 Hook,下午 5 点准时上台。

**现场细节**:Hook 用"双 11 凌晨 3 点值班电话"切入,
台下瞬间安静;Demo 段现场跑压测,峰值 12 万 RPS;
Q&A 收到 8 个问题,答出 7 个,第 8 个说"会后我邮件你"。
投票评分 4.6/5。会后 30+ 招聘意向,2 个客户合同。

### 8.2 案例 2:公司内部技术分享(从 5 人到 200 人)

**背景**:某中厂基础设施团队,内部 Tech Sharing 起步时仅 5 人旁听,
1 年后成为公司级技术品牌,峰值 200 人到场。

**关键转折点**:

1. **第 1 阶段(0-3 月)**:硬塞知识,反响差。
   听众说"听不太懂"。
2. **第 2 阶段(4-6 月)**:每场只讲 1 个 idea,
   从 60 min 缩到 30 min,鼓励 5 min Q&A。
   听众回到 20 人。
3. **第 3 阶段(7-12 月)**:引入"故事线 + 真实踩坑 + 现场 Demo",
   鼓励主讲人讲自己失败的尝试。
   听众增至 80 人,有人专程跨城参加。
4. **第 4 阶段(13-18 月)**:固定每周二 12:00,
   内容同步录屏上传知识库,
   出现"二刷观众"+ 高频问题 top10。

### 8.3 案例 3:Lightning Talk 5 分钟演讲实战

**背景**:PyCon China 闪电演讲,主题"用 5 行 Python 替代 50 行 Go",
台下 500 人,5 分钟超时一票否决。

**极致取舍**:

1. **不要 Hook**,直接抛结论:"5 行 Python = 50 行 Go"
2. **不要 What 段**,假设听众已知道
3. **How 段**只有代码演示,3 分钟代码 + 1 分钟现场跑通
4. **Trade-off** 1 句话:"别在生产环境用"
5. **Take-away** 一句话:"用对地方,你就是英雄"

**经验**:5 分钟没有彩排空间,**必须预演 3 遍以上**。
我的试讲从 5 分钟一路压缩到 4:30,然后再压缩回 4:50,
给 Q&A 留缝。

### 8.4 案例 4:线上直播分享 1 万观众

**背景**:某技术博主在 B 站直播"云原生架构入门",
在线峰值 1.2 万,弹幕密度 200 条/min。

**线上 vs 线下的差异**:

1. **看不见听众**:眼神接触失效,改为"看镜头"。
2. **节奏快**:听众注意力更短,15 分钟无刺激就走。
3. **弹幕互动**:可展示弹幕选择下一段内容。
4. **容错率低**:一次卡顿/模糊,弹幕立刻刷"翻车"。
5. **回放价值**:直播后剪 10 分钟精华,二次传播。

**核心动作**:

- Hook 段用"今天我送你 3 招"形式立 flag,弹幕扣 1。
- 每 10 分钟喊一次互动:"懂扣 1"。
- Demo 改用预录视频,可重放。
- 结尾引导关注 + 三连,转化率从 1% 提到 4%。
